# 한마음 개발 워크플로우

## 1. 이슈와 브랜치

- 관련 이슈가 있으면 재사용한다. 새 이슈 제목은 `[Type] 작업 내용`으로 작성하고 담당자와 라벨을 지정한다.
- 일반 작업은 최신 `dev`에서 `type/이슈번호-작업명` 형식으로 분기한다. 브랜치의 작업명은 영어 소문자와 하이픈을 사용한다. 예시는 `feat/6-login-ui`다.
- 한 이슈와 브랜치에는 하나의 작업 범위를 담는다. 코드 변경은 작업 브랜치에 커밋하고 PR로 반영한다.

## 2. 검증과 커밋

- 변경 범위에 맞는 검증을 실행한다. 포맷, 빌드, 테스트 명령은 작업 중인 저장소의 개발 지침을 따른다. [FE 개발 지침](https://github.com/Team-Hanmaum/hanmaum-frontend/blob/dev/AGENTS.md) · [BE 개발 지침](https://github.com/Team-Hanmaum/hanmaum-backend/blob/dev/AGENTS.md) · [AI 개발 지침](https://github.com/Team-Hanmaum/hanmaum-ai/blob/dev/AGENTS.md)
- 관련 변경만 스테이징한다. 커밋 제목은 `type: 작업 내용 (#이슈번호)`로 작성하고, 본문에 변경 이유와 주요 변경 사항, 검증 결과를 적는다.

## 3. PR과 리뷰

- 일반 PR의 대상 브랜치는 `dev`다. 스택 PR은 합의한 부모 브랜치에서 작업하고 그 브랜치를 대상으로 PR을 연다.
- PR 제목은 `Type(#이슈번호): 핵심 작업 내용`으로 작성한다. 저장소의 PR 템플릿에 관련 이슈, 변경 내용, 실제 검증 결과를 적고 담당자와 라벨을 지정한다. 화면 변경을 검토하는 데 도움이 되면 스크린샷을 첨부한다.
- `dev`에 머지하려면 팀원 1명 이상의 승인과 저장소의 필수 검사 통과가 필요하다. 머지 이후 배포 조건은 [CI/CD 문서](ci-cd.md)를 참고한다.
