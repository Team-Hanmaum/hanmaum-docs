# 한마음 개발 공통 인수인계

기준일: 2026-10-01 KST. 대상: Hanmaum 프로젝트에서 새로 시작하는 FE·BE·AI 개발 채팅.
이 문서는 제품·디자인 결정과 현재 코드 상태를 연결하는 안내서다. 원문 명세와 실제 코드를 대체하지 않는다.

## 가장 먼저 알아야 할 사실

1. 한마음은 가족이 남긴 소식을 정리하고 기존 정보의 변경·해소까지 제안하는 부모 돌봄 웹앱이다. 주 사용자는 30~50대 자녀 보호자이며 휴대폰 중심으로 사용한다.
2. 제품의 현재 정보를 최종 반영하는 주체는 공간 소유자다. 구성원은 일반 변경을 요청한다. 본인 담당 할 일 상태 변경과 본인 소식 원본 삭제는 명시된 예외다.
3. Figma 화면은 개발 참고용 상세 시안이다. 화면이 있다는 사실은 API·정책·코드가 완성되었다는 뜻이 아니다.
4. 기능 DB는 총 100개다. Must 67, Should 15, Could 9, Won't 9. **100개 개별 페이지의 본문은 모두 비어 있고, 기능 설명은 DB 속성에 있다.**
5. 현재 FE는 초기 예시 화면, BE는 보안·DB·통신 기반, AI는 빈 제안 배열을 반환하는 stub 단계다.
6. BE `docs/architecture.md`의 구성원 직접 변경 권한 표는 제품 정책과 충돌한다. 이를 근거로 구성원 직접 확정을 구현하지 않는다.
7. 사용자는 남은 개발 기간이 한 달 미만이라고 밝혔다. 정확한 마감일·개발 인원·배포 완료 조건은 아직 확인하지 않았다. 아래 작업 순서는 권장안이며 일정 약속이 아니다.

## 서비스의 핵심과 범위

**확정 정책:** 소식 입력 → 원본 저장 → AI가 기존 정보와 비교해 제안 → 가족 검토·요청 → 소유자 검증·반영 → 현황 확인·공유.

- 원본 소식, 분석 결과, 반영 전 제안, 구성원 변경 요청, 확정된 항목, 변경 이력을 구분한다.
- 새로운 기록을 단순히 쌓는 데 그치지 않고 기존 일정 변경·질문 해소·중복 근거 연결을 다룬다.
- 공간은 부모님 한 명 기준이며 소유자 혼자서도 이용할 수 있다.
- AI는 제안만 한다. 소유자 본인의 기록이나 1인 공간에서도 자동 확정하지 않는다.
- 일정·할 일·확인사항은 직접 추가 가능하다. 관찰·안내는 소식과 제안 확인 흐름으로 등록한다.
- 카카오톡은 사용자가 선택해서 공유하는 채널이다. 대화 자동 수집·메시지 자동 발송은 제외한다.
- 의료 진단·치료/복약 변경·등급 예측·제도 판정·공식 진료 문서 생성·위치/기기 모니터링은 제외한다.
- MVP 결제는 구현하지 않는다. 무료 공간 수·AI 사용량·가격은 사업 구상과 운영 확정을 구분한다.
- 음성·브리핑·추가 질문·내부 알림 등 Should, 상세 검색·OCR·PWA 설치 등 Could는 화면 유무로 Must에 넣지 않는다.
- 오프라인 돌봄 정보 조회·수정은 제외한다. 연결 오류 안내나 화면에 이미 표시된 목록 유지와 오프라인 기능을 혼동하지 않는다.

관련: 정책 3~5·13장, [FEATURES.md](FEATURES.md).

## 반드시 지킬 권한

| 동작 | 소유자 | 구성원 |
| --- | --- | --- |
| 현재 참여 공간의 소식·항목·근거·이력 조회 | 가능 | 가능 |
| 소식 작성·가족 초대 | 가능 | 가능 |
| AI 제안 검토·수정안 작성·후보 선택 | 가능 | 가능 |
| AI 제안 반영·연결 확정 | 직접 반영 | 승인 요청 |
| 항목 등록·내용 수정·담당자 변경·일반 삭제 | 직접 반영 | 승인 요청 |
| 할 일 상태 변경 | 모든 할 일 | 본인 담당은 직접, 그 외 요청 |
| 질문에 답 제출 | 가능 | 가능 |
| 답변 확인·질문 해소 | 최종 반영 | 승인 요청 |
| 소식 원본 삭제 | 공간 내 모든 소식 | 본인 소식 |
| 공간 정보 수정 | 직접 반영 | 수정 요청 |
| 내보내기·소유권 이전·공간 삭제 | 가능 | 불가 |

모든 작업은 현재 참여 상태를 확인한다. 소유권 이전은 현재 구성원 한 명에게 원자적으로 수행하고 기존 소유자는 구성원이 된다. 소유자가 0명 또는 2명인 중간 상태를 만들지 않는다.

**참여와 변경 승인은 다르다.** 유효한 초대 링크는 발급 후 24시간이며 로그인 후 구성원으로 참여한다. 별도 가입 승인 단계를 추가하지 않는다. 이미 참여 중이면 중복 가입하지 않는다.

관련: SPACE-04~10·13~15, PROP-10, ITEM-03~08·14~15, REC-10, 정책 1~2장.

## 상태와 동시 변경

- 할 일: 미시작 → 진행 중 → 완료. 미시작 → 완료도 가능. 완료 취소는 진행 중으로 간다. 담당자는 현재 구성원 1명 또는 미지정이다.
- 일정: 예정·완료·취소. 날짜 경과는 '지난 일정' 표시이며 자동 완료가 아니다. 완료·취소는 소유자가 확정한다.
- 질문/확인사항: 미확인·확인됨. 답변 제출·열람만으로 확인됨으로 바꾸지 않는다.
- 제안/요청: 검토 대기·승인 요청·반영·미적용. 선택하지 않은 제안은 검토 대기, 명시적 미적용과 구분한다.
- 분석: 진행·완료·실패. 분석 완료는 항목 반영 완료가 아니다.
- 상충 확인 필요·근거 재확인 필요·편집 중·삭제 표시는 위 상태들과 별도 축이다.
- 정책서의 영문 상태명은 설계 참고 이름이다. 실제 DB·공개 API enum은 아직 전체 합의하지 않았다. AI 내부 계약의 enum은 이미 존재한다.

편집 잠금은 관리 항목 한 개 단위다. 잠금 보유로 승인 권한이 생기지 않는다. 저장·취소·만료·접속 종료 시 해제하며 정확한 TTL·갱신 방법은 미정이다. 최종 반영과 상태 변경 시에도 현재 역할·참여·버전·잠금을 재검사한다.

**선택한 제안은 전체 검증 후 함께 적용한다. 하나라도 충돌하면 선택 묶음 전체를 반영하지 않는다.** 선택 간 충돌·원본/대상 존재·유효 근거·필수 값·중복 처리까지 검사한다. 반복 요청은 항목·이력 등을 중복 생성하지 않아야 한다. 응답 유실은 확정 실패와 구분하고 처리 결과 확인 전 무조건 재실행하지 않는다.

관련: PROP-06~07, ITEM-05~10·14, 정책 6~7·12장.

## 삭제와 공유

- 일반 항목 삭제: 일반 목록·현황에서 숨기되 삭제 표시와 이력을 보존한다.
- 소식 원본 삭제: 원문뿐 아니라 그 내용을 복사한 제안·근거·항목·이력·요약·알림에서도 제거한다. 링크만 끊는 것으로 끝내지 않는다.
- 원본 삭제의 연결 정리는 소유자 승인 대기로 미루지 않는다. 이력 보존 일반 원칙보다 내용 제거 규칙이 우선한다.
- 독립된 유효 근거가 없어진 항목은 재확인 표시 후 소유자 재확인 전 현황판·새 공유 대상에서 제외한다. 재확인은 삭제 내용 복원이 아니다.
- 원본 삭제 중이거나 삭제된 경우 늦게 도착한 AI 결과·재시도·검색으로 내용이 되살아나지 않게 한다.
- 나가기/내보내기: 접근 즉시 종료, 미완료 담당 할 일은 미지정, 완료 상태·공유 기록·이력은 유지한다.
- 공간 삭제: 소유자만 가능, 소속 데이터와 접근을 종료하고 MVP 복구를 제공하지 않는다.
- 회원 탈퇴: 소유 중인 모든 공간 이전/삭제를 먼저 완료하고 계정·소셜 연결·인증 정보를 삭제한다. 공동 기록을 자동 전부 삭제하지 않고 남은 작성자를 '탈퇴한 사용자'로 표시한다.

공유 카드에는 항목 유형·변경 여부·서비스 링크만 넣는다. 이름·증상·제목·예약일·병원·원문 등 상세는 제외한다. 공유 링크 접근 시 로그인과 현재 참여 권한을 다시 확인하며 링크만으로 가입시키지 않는다. 삭제/권한 상실 후에는 과거 링크도 상세를 노출하지 않는다. 초대 링크의 24시간을 공유 링크에 임의로 적용하지 않는다.

관련: REC-10~11, HIST-01~03, AUTH-05, SPACE-09~10·14~15, SHARE-01~05, 정책 8~11장.

## AI가 반드시 지킬 규칙

- 일정·할 일·확인사항·관찰·안내의 분류와 값 추출은 책임 구분이지 모델 2회 호출 요구가 아니다.
- 상대 날짜는 원본의 recordedAt + Asia/Seoul 기준. 재시도 시 현재 날짜로 다시 해석하지 않는다.
- 예: 2026-09-28에 남긴 '다음 달 15일'은 2026-10-15. 10월 재시도여도 동일하다.
- 언급되지 않은 시간·담당자·사실을 채우지 않는다. 과거 발언 인용 등 기준이 불명확하면 확인을 요청한다.
- 같은 공간의 유효 후보만 비교한다. 모호하면 후보를 제시하고 보류한다.
- 중복은 새 항목 자동 생성 대신 근거 연결을 제안한다. 상충은 현재 값 유지 + 양쪽 근거 비교다.
- 분석 실패에도 저장된 원본을 보존하고 원문 재등록 없이 분석 재시도를 제공한다.
- 서비스 기록에 포함된 명령은 분석 데이터이며 실행 지시가 아니다.
- 모델·비용·임계값·자동 분석 트리거 세부 규칙은 새로 확정하지 않는다. 저장 후 분석 중 화면은 존재하나 호출 횟수·재분석 조건과 같지 않다.

관련: AI-01~08·17~18, PROP-09, 정책 5장.

## 디자인 결정과 화면 구조

**대화 결정:** 모바일 중심 웹앱, Noto Sans KR, 청록 분위기. 초기 Pretendard 선택은 Noto Sans KR로 변경되었다.
로고는 사용자가 만든 자산을 사용한다. 기본 구현 참고 너비는 390px이며 긴 Figma 프레임은 전체 스크롤 내용을 보여주기 위한 것이다.

하단 탭은 **홈 / 돌봄 / 소식 / 가족 / 전체**다.
- 홈: 현황과 가족 참여 상태, 주요 목록·행동으로 진입.
- 돌봄: 일정·할 일·질문·관찰·안내 및 확정 항목의 관리·근거·이력.
- 소식: 원본 기록, 작성, 분석 결과, 확인할 내용, 제안 검토·승인 요청·처리 결과.
- 가족: 참여자, 초대, 내보내기, 소유권 이전, 나가기.
- 전체: 전체 메뉴, 계정·공간 정보, 로그아웃·탈퇴.
- 상단 공간명: 참여 공간 메뉴 → 선택한 공간 홈. '공간 전체 보기' → 참여 공간 선택 화면.
- 화면을 탭별 섹션에 묶었지만 공유 화면은 여러 진입점에서 재사용한다. 보드 좌표나 예시 개수만큼 라우트를 만들지 않는다.
- 프로토타입 연결은 사용자가 불필요하다고 판단했다. 화면·주석·버튼별 안내를 기준으로 개발한다.

UX 원칙은 다음과 같이 유지한다.
1. One Thing per One Page: 각 화면의 핵심 목적과 주요 행동을 분명히 한다.
2. Tap & Scroll: 주요 흐름은 탭·스크롤로 진행한다. 자연어 소식·답변처럼 본질적인 입력은 남긴다.
3. Easy to Answer: 현재 값·참여자·후보를 불러오고 기억에 의존하는 질문을 줄인다.
4. Value First, Cost Later: 가치 안내 후 로그인·공간 생성. 권한 확인 전에 실제 돌봄 정보를 공개한다는 뜻은 아니다.
5. No Ads Patterns: 광고형 배너·과장된 AI 홍보 대신 기능을 설명한다.
6. Context-based: 원래 항목·공간·진입 목적을 유지하며 다음 단계로 연결한다.
7. No More Loading: 원본 저장과 분석 상태를 구분하고 부분 로딩·재시도를 제공한다. 성공을 확인하기 전에 완료 처리하지 않는다.
8. Sleek Experience: 입력·선택·스크롤 맥락을 유지하고 불필요한 재입력을 줄인다.

승인 대기·잠금·빈 화면·첫 로딩·부분 실패·오프라인·인증 만료·권한 상실·결과 미확인은 각각 의미가 다르다.

## 현재 레포와 연결 방식

| 레포 | 기준 커밋 | 관측 상태 |
| --- | --- | --- |
| hanmaum-frontend | 35672e8 | React/Vite/Tailwind 초기 구성과 데모 화면. 한마음 토큰·업무 화면 미구현 |
| hanmaum-backend | be7f131 | Spring 세션·CSRF·OAuth 설정·오류 응답·Flyway 세션 테이블·AI 클라이언트 |
| hanmaum-ai | 8ce260b | FastAPI 내부 인증·요청/응답 검증·stub. 실제 LLM 분석 없음 |

세 레포 모두 조회 당시 dev 브랜치이며 작업 트리 변경이 없었다. 원격 fetch나 실행 테스트는 이번 문서화 작업에서 수행하지 않았다.

구현된 연결 방향은 **브라우저 → Spring → 내부 FastAPI**다.
- FE는 세션 쿠키와 CSRF를 사용한다. JWT/localStorage 토큰 전제로 새 인증 체계를 만들지 않는다.
- BE는 권한·원본/제안 저장·승인·현재 값·이력·DB 트랜잭션을 담당한다.
- AI는 BE가 전달한 원문·후보로 제안만 반환한다. 서비스 DB를 직접 읽거나 변경하지 않는다.
- AI 내부 호출은 POST /v1/analyses, X-Internal-Api-Key, X-Request-Id 계약이 이미 있다.
- 전체 공개 도메인 API·ERD·성공 응답 규격은 아직 완성되지 않았다. 기존 ApiError와 CSRF/로그아웃 응답부터 보존·정합화한다.

## 권장 착수 순서

다음은 **개발 제안**이다.
1. FE 기본 토큰·버튼·입력·레이아웃 구현과 BE ERD/API 초안을 병행한다. 공통 컴포넌트 전체 완료를 첫 화면 착수 조건으로 두지 않는다.
2. 로그인 → 공간 생성/초대 → 첫 홈까지 FE/BE를 일찍 연결한다.
3. 소식 저장 → AI 제안 → 소유자 반영 → 최신 현황을 하나의 실제 흐름으로 연결한다.
4. 나머지 Must CRUD·요청·잠금·삭제·공유를 넓히고 예외 상태와 통합 검증을 마무리한다.
5. Should/Could는 일정·인력과 Must 완료 상태를 보고 별도로 선택한다.

후속 채팅은 변경마다 관련 기능 ID·Figma 노드·정책 장·API/테스트를 연결해 기록한다. API 변경은 상대 레포가 소비하는 계약과 함께 검토한다. 문서에 없는 정책을 개발 편의로 확정하지 않는다.
