## 0. 용어 정의

| 용어 | 뜻 |
| --- | --- |
| **돌봄 공간** | 부모님 한 명을 기준으로 소식과 현재 돌봄 정보를 함께 관리하는 단위. 각 공간의 정보와 권한은 분리한다. |
| **소유자 (OWNER)** | 공간의 최종 반영·관리 권한을 가진 한 명의 사용자. 최초에는 생성자이며 소유권 이전 가능. |
| **구성원 (MEMBER)** | 초대받아 공간에 참여한 가족. 소식 작성·검토·변경 요청, 본인 담당 할 일 직접 등록 및 상태 변경 가능. |
| **소식 / 원본 기록** | 가족이 직접 남긴 자연어 입력과 작성자·등록 시점. AI 분석 결과와 별도로 보존하는 근거. |
| **관리 항목** | 소유자가 확인해 현재 정보로 관리하는 일정·할 일·확인사항·관찰·안내. |
| **AI 제안** | 소식을 분석해 생성한 추가·변경·해소·연결 후보. 생성만으로 현재 정보가 바뀌지 않음. |
| **변경 요청** | 구성원이 등록·수정·삭제·연결·답변 등의 최종 반영을 소유자에게 요청한 내용. |
| **반영 / 확정** | 소유자가 내용을 확인해 실제 관리 항목에 적용한 상태. 본인 담당 할 일 직접 등록과 상태 변경은 별도 예외. |
| **확인 필요 / 재확인 필요** | 상충하거나 유효한 근거가 사라져 소유자의 추가 확인이 필요한 표시. 완료·취소와 별개. |
| **근거 / 변경 이력** | 판단에 사용한 원본·직접 입력과 누가 언제 무엇을 바꿨는지에 대한 기록. |

## 1. 사용자 · 로그인 · 권한 정책

**관련 기능:** `AUTH-01` · `AUTH-02` · `AUTH-03` · `AUTH-04` · `AUTH-05` · `SPACE-08` · `SPACE-15`

### 1.1 로그인과 접근

- **Google · Kakao 소셜 로그인**을 지원하며 최초 로그인 시 계정을 생성한다. 같은 제공자와 제공자 사용자 ID는 기존 회원으로 연결하고, 이메일만 같다는 이유로 서로 다른 소셜 계정을 자동 병합하지 않는다.
- 표시 이름은 최초 가입 때 Google 이름·Kakao 닉네임을 저장하며, 값이 없으면 null로 둔다. 재로그인으로 기존 표시 이름을 덮어쓰지 않는다.
- 새로고침·재접속 시 유효한 로그인 상태를 유지하고, 인증 만료 시 재로그인을 안내한다.
- 로그아웃하면 인증이 필요한 공간·소식·관리 항목에 접근할 수 없다.
- 기본 사용자 정보와 로그인 방식을 조회할 수 있다. 다른 가족의 돌봄 정보는 **현재 참여 중인 공간** 안에서만 조회한다.
- 초대·공유 링크를 갖고 있다는 이유만으로 돌봄 정보 열람 권한을 부여하지 않는다.

### 1.2 공간 역할

| 역할 | 설명 | 최종 반영 권한 |
| --- | --- | --- |
| **소유자 (OWNER)** | 공간마다 한 명. 생성자 또는 소유권을 이전받은 구성원 | AI 제안·연결·관리 항목 등록·수정·삭제·답변 해소·공간 정보 수정 |
| **구성원 (MEMBER)** | 유효한 초대를 통해 참여한 가족 | 일반 변경은 승인 요청. 본인 담당으로 새 할 일을 직접 등록하고, 본인에게 배정된 할 일의 상태를 직접 변경할 수 있음 |

### 1.3 권한 기준표

| 작업 | 소유자 | 구성원 |
| --- | --- | --- |
| 공간·소식·항목·근거·이력 조회 | 가능 | 참여 공간에서 가능 |
| 소식 작성 / 가족 초대 | 가능 | 가능 |
| AI 제안·연결 후보 검토 / 수정안 작성 | 가능 | 가능 · 최종 반영 요청 |
| AI 제안 반영 / 연결 확정 | 가능 | 직접 불가 · 승인 요청 |
| 항목 등록·내용 수정·담당자 변경·삭제 | 가능 | 본인 담당 새 할 일 직접 등록 가능 · 그 외 등록과 기존 항목의 내용 수정·담당자 변경·삭제는 승인 요청 |
| 할 일 진행 상태 변경 | 모든 할 일 가능 | 본인 담당만 직접 가능 · 나머지는 요청 |
| 확인사항 답변 제출 / 해소 확정 | 답변 제출 시 승인 대기 · 별도 반영으로 해소 확정 | 답변 제출 시 승인 대기 · 소유자가 해소 확정 |
| 소식 원본 삭제 | 공간 내 모든 소식 | 본인 소식만 가능 |
| 돌봄 대상·공간 정보 수정 | 가능 | 수정 요청 |
| 구성원 내보내기 / 소유권 이전 / 공간 삭제 | 가능 | 불가 |
| 공간 나가기 | 소유권 이전 또는 공간 삭제 후 가능 | 가능 |

> **구성원이 직접 수행할 수 있는 권한 예외**
>
> - 구성원은 **본인을 담당자로 지정한 새 할 일**을 소유자 승인 없이 직접 등록할 수 있다.
> - 구성원은 **본인 담당 할 일의 진행 상태**를 직접 변경할 수 있다.
> - 구성원은 **본인이 작성한 소식 원본**을 직접 삭제할 수 있다. 삭제 영향은 11장의 연결 정보 정리 규칙을 따른다.
> - 일반 관리 항목 삭제와 원본 소식 삭제는 서로 다른 작업이다.

## 2. 돌봄 공간 · 가족 정책

**관련 기능:** `SPACE-01` · `SPACE-02` · `SPACE-03` · `SPACE-04` · `SPACE-05` · `SPACE-06` · `SPACE-07` · `SPACE-09` · `SPACE-10` · `SPACE-11` · `SPACE-12` · `SPACE-13` · `SPACE-14` · `SPACE-15`

### 2.1 공간 생성과 기본 정보

- 공간은 **부모님 한 명**을 기준으로 생성하고 생성자를 소유자로 지정한다.
- 돌봄 대상 호칭은 필수다. 앞뒤 Unicode 공백 제거 후 1\~30자(Unicode 코드 포인트)로 제한하고 줄바꿈을 허용하지 않는다. 내부 공백·대소문자는 유지한다.
- **같은 사용자가 현재 소유한 공간 사이의 동일 호칭을 금지**한다. 다른 소유자의 공간과는 중복을 허용한다. 생성·호칭 변경·소유권 이전 시 같은 기준을 적용한다.
- 현재 사용자별 공간 생성 개수 제한은 두지 않는다. 동일 생성 요청의 재전송은 기존 결과를 반환하며 공간을 중복 생성하지 않는다.
- 가족 초대 전에도 소유자 혼자 소식 기록·AI 검토·항목 관리 가능.
- 사용자는 본인이 참여한 공간 목록에서 공간을 선택하고 돌봄 대상·기본 정보·구성원 역할을 확인한다.
- 돌봄 대상·공간 정보 변경은 소유자가 최종 반영한다. 구성원의 수정 요청만으로 기본 정보가 바뀌지 않는다.

### 2.2 가족 초대와 참여

> **초대 링크 유효기간: 발급 시점부터 24시간**
>
> ---
>
> - 소유자와 구성원 모두 본인이 참여 중인 공간의 초대 링크를 발급할 수 있다.
> - 링크 진입 → 소셜 로그인 → 초대 흐름 복귀 → 링크·공간의 유효성 확인 → 구성원으로 참여. 참여 전에는 부모님·가족 이름과 돌봄 내용을 노출하지 않는다.
> - 만료된 링크로는 참여할 수 없고, 현재 구성원에게 새 링크 발급을 요청한다.
> - 이미 참여한 사용자도 처음 확인·참여하는 요청에서는 링크 유효성을 먼저 검증한다. 유효하면 중복 등록 없이 기존 공간으로 이동하고, 만료되면 만료 안내 후 참여 공간 목록으로 접근한다.
> - 새 링크를 발급해도 기존 링크는 각자의 만료 시각까지 유지한다. 한 링크를 여러 사람이 사용할 수 있으며 별도 사용 횟수·공간 인원 제한을 추가하지 않는다.
> - 발급자의 참여가 종료되면 그 참여 중 발급한 링크는 사용할 수 없으며, 발급자가 재참여해도 되살리지 않는다.
> - 삭제된 공간의 링크는 사용할 수 없다. 초대 링크와 항목 공유 링크는 구분한다.
> - 초대 발급·참여의 동일 요청 재전송으로 링크나 참여를 중복 생성하지 않고 만료 시각도 연장하지 않는다.

### 2.3 나가기와 내보내기

- 구성원은 스스로 공간에서 나갈 수 있고, 소유자는 구성원을 내보낼 수 있다.
- 처리 이후 해당 공간의 조회·수정·공유 링크 접근 권한을 종료한다.
- 떠난 구성원이 맡던 **미시작·진행 중 할 일은 담당자 미지정**으로 전환한다.
- 완료된 할 일의 상태와 기존 변경 이력은 유지한다. 나가기·내보내기만으로 작성한 소식을 자동 삭제하지 않는다.
- 권한이 종료된 사용자는 기존 화면·링크로도 새로운 요청이나 변경을 실행할 수 없다.
- 스스로 나갔거나 내보내진 사용자는 **마지막 참여 종료 이후 발급된 유효한 새 초대**로 재참여할 수 있다. 과거에 성공한 참여 요청을 재전송해 종료된 참여를 복원하지 않는다.

### 2.4 소유권 이전과 공간 삭제

- 소유권은 **현재 참여 중인 구성원 한 명**에게 이전할 수 있다.
- 이전이 완료되면 새 소유자가 승인·관리 권한을 받고, 기존 소유자는 일반 구성원으로 전환한다. 새 소유자가 이미 같은 호칭의 공간을 소유했다면 이전을 허용하지 않는다.
- 소유자가 없거나 두 명이 되는 중간 상태를 만들지 않는다.
- 소유자는 소유권을 이전하거나 공간을 삭제한 뒤에 나가기·회원 탈퇴 가능.
- 공간 삭제는 소유자만 실행하며 삭제 대상·영향 범위를 확인한다. **공간 복구는 MVP에서 제공하지 않는다.**

### 2.5 부모님 동의와 세부 권한

- **Should · 부모님 동의 요청:** 어떤 돌봄 정보를 저장하고 누가 열람하는지 알리고 동의를 받는 흐름 제공.
- 실제 돌봄 정보를 수집하기 전 필요한 안내·동의 절차를 마련한다. 동의 요청 화면의 개발 우선순위와 실제 데이터 수집 준비를 혼동하지 않는다.
- **Could · 정보별 세부 권한:** 요양보호사 등 가족 외 참여자의 정보별 열람 범위를 분리하는 확장. 기본 MVP의 OWNER·MEMBER 권한을 임의로 확대하지 않는다.

<a name="core-workflow"></a>

## 3. 핵심 사용 흐름

> **소식 입력 → AI 분석·기존 정보 연결 제안 → 가족 검토·요청 → 소유자 확인·반영 → 현황판·공유**

| 단계 | 사용자 행동 | 현재 정보 변경 여부 |
| --- | --- | --- |
| **① 소식 기록** | 가족이 원문을 작성하고 저장 | 소식만 저장 · 기존 항목은 유지 |
| **② 분석과 제안** | AI가 항목 유형·세부 값·기존 연결 후보와 근거를 제시 | 변경 없음 |
| **③ 가족 검토** | 구성원이 후보 선택·수정·답변을 검토해 요청 제출 | 승인 대기 · 변경 없음 |
| **④ 소유자 반영** | 선택한 제안·요청의 근거와 최신 상태 확인 후 적용 | 검증 통과한 선택 묶음만 반영 |
| **⑤ 현황 확인·공유** | 가족이 최신 항목·담당자·이력을 확인하고 직접 공유 | 조회·공유만으로 상태 변경 없음 |

- 소유자는 자신의 소식도 분석 결과를 확인한 뒤 반영한다. 1인 공간에서도 AI가 스스로 확정하지 않는다.
- 일정·할 일·확인사항은 직접 입력할 수 있다. 구성원이 본인을 담당자로 지정한 새 할 일은 직접 등록하고, 그 외 등록은 소유자 승인 요청으로 처리한다.
- 본인 담당 할 일의 직접 등록·상태 변경과 허용된 원본 삭제는 1.3의 직접 수행 권한을 따른다.

## 4. 소식 · 원본 기록 정책

**관련 기능:** `REC-01` · `REC-02` · `REC-03` · `REC-04` · `REC-05` · `REC-06` · `REC-07` · `REC-08` · `REC-09` · `REC-10` · `REC-11`

### 4.1 작성과 보존

- 소유자와 구성원 모두 병원 방문·기관 상담·부모님 상태 등 소식을 자연어로 작성한다.
- 한 소식에 여러 내용이 들어갈 수 있으며 사용자가 일정·할 일별로 먼저 나누어 입력할 필요는 없다.
- 원문·작성자·등록 시점은 AI 분석·반영 여부와 별도로 저장한다.
- 소식 목록과 상세에서 원문·등록 정보 및 연결된 분석·제안을 확인한다.
- AI 결과를 수정해도 원본 기록 자체를 덮어쓰지 않는다. 원본 삭제는 11장의 별도 규칙을 따른다.

### 4.2 확장 입력과 분류

| 우선순위 | 기능 | 적용 규칙 |
| --- | --- | --- |
| **Should** | 음성 입력 | 음성을 텍스트로 변환한 뒤 사용자가 확인·수정하고 소식으로 등록 |
| **Could** | 문서·이미지 인식 | 인식 결과를 입력 초안으로 제공하고 사용자 확인 후 등록 |
| **Could** | 영역 분류 | 병원·기관·행정·생활·비용 체계를 사용하되 관리 항목과 분류 값을 각각 관리 · 자동 상속 없음 |
| **Could** | 소식 검색·필터 | 소식 원본을 기간·작성자·영역으로 검색 · 항목 검색과 분리 · 삭제 원문 제외 |

- 카카오톡 대화 자동 수집은 **Won’t** 범위로 둔다. 사용자가 직접 입력한 소식을 기준으로 처리한다.

## 5. AI 분석 · 기존 정보 연결 정책

**관련 기능:** `AI-01` · `AI-02` · `AI-03` · `AI-04` · `AI-05` · `AI-06` · `AI-07` · `AI-08` · `AI-09` · `AI-10` · `AI-11` · `AI-17` · `AI-18` · `PROP-08` · `PROP-09`

### 5.1 분석 결과의 범위

- 먼저 일정·할 일·확인사항·관찰·안내로 **항목 유형을 분류**하고, 각 항목의 날짜·시간·내용·질문 등 **세부 값을 추출**한다.
- 유형 분류와 값 추출은 역할을 구분한 것이며, AI 호출을 반드시 두 번으로 나누라는 뜻은 아니다.
- 같은 공간의 유효한 기존 항목과 비교해 **추가·변경·해소·연결 후보**를 만든다. 일정 취소·상태 변경도 변경 제안에 포함한다.
- 각 제안에 원문 근거와 대상 항목을 연결한다. 입력에 없거나 근거가 부족한 사실은 확정 정보로 제시하지 않는다.
- 불분명한 연결은 후보와 불확실한 내용을 보여주고 소유자가 최종 결정한다. 적절한 대상이 없으면 보류한다.

### 5.2 날짜·시간 해석

> **상대 날짜의 기준은 소식 등록 시점 + Asia/Seoul**
>
> ---
>
> - “다음 달 15일”, “다음 주 화요일”은 소식 등록 시점을 기준으로 해석한다.
> - 같은 소식을 나중에 다시 분석해도 기준 시점이 바뀌지 않는다.
> - 예: 2026년 9월 28일 등록한 “다음 달 15일”은 **2026년 10월 15일**로 제안한다. 10월에 재시도해도 11월로 밀리지 않는다.
> - 과거 대화를 인용하거나 기준 시점이 불명확한 경우에는 임의 날짜를 확정하지 않고 확인을 요청한다.
> - 언급되지 않은 시각·담당자 등은 추측해서 채우지 않는다.

### 5.3 중복과 상충

| 구분 | 처리 | 확정 주체 |
| --- | --- | --- |
| **중복 후보** | 기존 항목과 의미가 같으면 새 항목을 자동 생성하지 않고 기존 항목에 근거를 연결하는 안 제시 | 소유자가 연결·반영 결정 |
| **상충 후보** | 날짜·내용이 다르면 양쪽 근거와 확인 필요 표시 제공 · 최신 소식만으로 덮어쓰지 않음 | 소유자가 근거 비교 후 결정 |
| **대상 불명확** | 가능한 항목 후보 제시 · 명확해질 때까지 적용 보류 | 구성원은 연결 요청 · 소유자가 최종 선택 |

- 상충이 발견되어도 현재 값은 유지한다. 확인 필요 표시로 불확실성을 알리고, 승인된 변경만 새 현재 값으로 반영한다.

### 5.4 실패·재시도·원본 삭제

- 분석 진행·완료·실패를 표시하고 실패 시 원본을 유지한 채 재시도를 제공한다.
- 재시도만으로 현재 정보가 바뀌거나 같은 제안·항목이 중복 생성되지 않도록 한다.
- 형식·유형·필수 값·근거 연결이 유효하지 않은 결과는 정상 제안으로 확정하지 않는다.
- 분석 도중 원본이 삭제되면 분석을 중단하거나 결과를 폐기한다. 삭제된 내용이 늦게 도착한 결과로 다시 나타나지 않게 한다.

### 5.5 Should AI 기능

- **근거 기반 질문 응답:** 유효한 현재 정보와 기록으로 답하고 출처 표시. 삭제된 내용과 근거 재확인 전 정보는 확정 근거로 사용하지 않는다.
- **새 참여자 브리핑:** 현재 일정·남은 할 일·미확인 사항·최근 변경을 요약하고 관련 근거로 연결한다.
- **추가 확인 질문:** 사용자 발언에서 추출한 질문과 AI가 제안한 질문을 구분한다. 선택만으로 자동 등록하지 않고 소유자 승인 후 확인사항으로 추가한다.

## 6. 제안 검토 · 승인 · 동시 편집 정책

**관련 기능:** `PROP-01` · `PROP-02` · `PROP-03` · `PROP-04` · `PROP-05` · `PROP-06` · `PROP-07` · `PROP-08` · `PROP-10` · `ITEM-10`

### 6.1 검토와 승인 요청

- 제안의 유형·대상·변경 전후 값·원본 근거를 함께 보여준다.
- 소유자와 구성원 모두 제안을 검토하고 연결 대상을 고르거나 반영할 내용을 수정할 수 있다.
- 구성원의 선택·수정·답변은 **변경 요청**으로 제출한다. 현재 정보에는 즉시 적용하지 않는다.
- 소유자는 요청과 최신 정보를 비교한 뒤 반영하거나 미적용 결정한다.
- 수정 가능한 값은 항목별 내용·날짜·담당자 등 사용자 입력 값으로 한정하며, 원본·작성자·시점·분석 근거를 임의로 변조하지 않는다.

### 6.2 개별 선택과 미적용

- 여러 제안 중 **반영할 제안만 개별 선택**하고 필요한 내용을 수정한 뒤 적용한다.
- 선택하지 않은 제안은 원본·대상·근거와 검토에 사용한 항목 버전이 유효하면 검토 대기로 남긴다. 다른 제안을 반영해 검토에 사용한 항목의 버전이 바뀌거나 원본·대상·근거가 무효가 되면 해당 제안도 무효로 표시한다. 선택 해제와 명시적인 미적용 처리는 구분한다.
- 소유자가 받아들이지 않기로 결정한 제안은 미적용으로 표시한다.
- 보류·미적용·단순 열람은 현재 항목의 내용이나 상태를 바꾸지 않는다.

### 6.3 선택 묶음의 적용 기준

> **선택한 제안은 전부 검증한 뒤 함께 적용한다. 하나라도 충돌하면 모두 미반영한다.**
>
> ---
>
> 1. 현재 소유자 권한과 공간 참여 상태 확인.
> 2. 선택한 제안의 유효 근거 확인. 기존 대상이 있는 경우 대상의 존재 여부·최신 버전·소유자 본인의 유효한 편집 잠금 확인.
> 3. 필수 값·연결 대상·이미 반영된 요청 여부 및 선택 제안 간 충돌 검증.
> 4. 모두 유효할 때 선택 묶음의 결과와 이력을 함께 반영.
> 5. 실패 시 현재 정보 유지 및 문제가 된 제안·재확인 사유 안내.

- 문제 제안을 선택 해제하고 나머지만 다시 적용할 수 있다.
- 같은 적용 요청을 반복해도 항목·변경 이력·알림이 중복 생성되지 않아야 한다.
- 자동으로 일부만 성공 처리하거나, 검토하던 값과 다른 최신 값을 조용히 덮어쓰지 않는다.

### 6.4 항목별 편집 잠금

- 편집 잠금 단위는 **관리 항목 한 개**이며, 공간 전체를 잠그지 않는다.
- 누가 편집 중인지 표시하고 다른 사람의 동일 항목 동시 편집을 제한한다. 조회와 다른 항목 편집은 계속 가능하다.
- 저장·취소 시 잠금을 해제한다. 접속이 끊겨 해제 요청을 보내지 못하면 갱신이 중단되고 유효시간 만료 시 잠금이 자동 해제된다.
- **편집 잠금은 승인 권한을 부여하지 않는다.** 구성원이 잠금을 갖고 저장해도 일반 변경은 요청으로 남는다.
- 기존 항목의 최종 반영과 할 일 상태 변경 시 작업자 본인의 유효한 잠금과 대상의 최신 버전을 검증한다.
- 잠금 만료 후 남아 있는 화면에서는 다시 잠금·권한·최신 상태를 확인해야 한다.
- 서버 설정의 기본 잠금 유지 시간은 2분이고 권장 갱신 간격은 30초다.

### 6.5 반영할 수 없는 대표 상황

| 상황 | 처리 |
| --- | --- |
| 소유자 권한 없음 / 참여 종료 | 직접 반영 차단 · 현재 역할에 맞는 화면 안내 |
| 다른 사람이 대상 편집 중 | 편집자·잠금 상태 안내 · 해제 후 재확인 |
| 검토 중 대상 내용 변경 | 최신 값과 제안 재비교 · 덮어쓰기 금지 |
| 원본·대상 삭제 / 유효 근거 부족 | 제안 무효·재확인 안내 · 삭제된 내용 복원 금지 |
| 필수 값 누락 / 연결 대상 불명확 | 보완·선택 요청 · 반영 보류 |
| 이미 적용된 요청 재전송 | 기존 처리 결과 안내 · 추가 반영 금지 |

## 7. 돌봄 항목 · 상태 전환 정책

**관련 기능:** `ITEM-01` · `ITEM-02` · `ITEM-03` · `ITEM-04` · `ITEM-05` · `ITEM-06` · `ITEM-07` · `ITEM-08` · `ITEM-09` · `ITEM-11` · `ITEM-12` · `ITEM-14` · `ITEM-15`

### 7.1 항목 유형과 직접 등록

| 유형 | 의미 | 등록 방식 |
| --- | --- | --- |
| **일정** | 특정 날짜·시간의 방문·예약 등 | 소식 분석 후 승인 또는 직접 입력 후 승인 |
| **할 일** | 누군가 수행해야 할 행동 | 소식 분석 후 반영 또는 직접 입력. 소유자와 본인 담당으로 등록하는 구성원은 직접 등록, 그 외 구성원 입력은 승인 요청 |
| **확인사항** | 아직 답을 확인하지 못한 질문 | 소식 분석 후 승인 또는 직접 입력 후 승인 |
| **관찰** | 가족이 직접 보고 들은 상태·변화의 기록 | 소식 입력과 제안 확인 흐름 |
| **안내** | 병원·기관 등에서 전달받은 내용 | 소식 입력과 제안 확인 흐름 |

- 소유자는 직접 입력한 항목을 확인 후 등록한다. 구성원은 본인을 담당자로 지정한 새 할 일을 승인 없이 직접 등록한다. 일정·확인사항과 담당자가 미지정이거나 다른 사람으로 지정된 새 할 일은 승인 요청으로 제출한다.
- 관찰과 전달받은 안내를 구분하며 AI의 진단·치료 판단으로 바꾸지 않는다.
- 일반 목록에는 확정된 항목을 표시하고 검토 중 제안·요청과 구분한다.

### 7.2 할 일 담당자

- 한 할 일의 담당자는 **현재 공간의 구성원 한 명** 또는 **미지정**이다. 복수 담당자는 허용하지 않는다.
- 기존 할 일의 담당자 지정·변경은 소유자가 최종 반영한다. 구성원은 변경 요청을 제출할 수 있다. 본인 담당 새 할 일의 직접 등록은 7.1을 따른다.
- 담당자 미지정이어도 할 일을 보존하며, 미지정 상태 자체가 완료를 의미하지 않는다.
- 담당자가 나가거나 제외되면 미완료 할 일만 미지정으로 전환한다.

### 7.3 할 일 상태

> **미시작 → 진행 중 → 완료**

| 전환 | 규칙 |
| --- | --- |
| 미시작 → 진행 중 | 소유자 또는 현재 담당자가 직접 변경 |
| 진행 중 → 완료 | 소유자 또는 현재 담당자가 직접 변경 |
| 미시작 → 완료 | 바로 완료 처리 허용 |
| 완료 → 진행 중 | 완료 취소 시 적용 · 이력 보존 |

- 다른 구성원은 직접 상태를 바꾸지 않고 요청한다.
- 완료 취소 시 미시작으로 초기화하지 않는다. 기본 전환 외의 되돌리기는 이번 상태 전환 규칙에 포함하지 않는다.
- 상태 변경은 편집 잠금·최신 상태·현재 권한을 확인한 뒤 처리한다.

### 7.4 일정 상태

- 일정 상태는 **예정 · 완료 · 취소**로 구분한다.
- 날짜·시간이 지나도 자동으로 완료하지 않는다. 미완료 일정은 **지난 일정**으로 나누어 보여준다.
- “지난 일정”은 날짜에서 계산한 표시이며 별도의 완료 상태가 아니다.
- 실제 완료·취소는 소유자가 직접 확인하거나 구성원의 요청을 승인해 처리한다.
- 취소는 예정 현황에서 제외하되 일정과 변경 이력을 남긴다. 잘못 등록한 항목을 숨기는 **삭제**와 구분한다.

### 7.5 확인사항 상태

- 확인사항은 **미확인 · 확인됨**으로 관리한다.
- 소유자와 구성원이 제출한 답변과 근거는 승인 대기로 저장하고, 질문은 미확인 상태를 유지한다. 답변 제출에는 편집 잠금이 필요 없다.
- 소유자가 기존 질문의 최신 버전과 본인의 유효한 편집 잠금을 확인한 뒤 답변 또는 AI 해소 제안을 반영하면 확인됨으로 전환한다.
- 단순 열람·알림 읽음·링크 클릭만으로 확인됨 처리하지 않는다.

### 7.6 수정·삭제와 탐색

- 확정 내용 수정·삭제는 소유자가 최종 처리하고 구성원은 요청한다.
- 일반 항목 삭제는 삭제 표시로 목록·현황판에서 숨기며 이력을 남긴다. 원본 삭제에 따른 내용 제거는 11장을 우선 적용한다.
- **Could:** 관리 항목의 영역은 소식과 같은 체계를 사용하되 자동 상속하지 않는다.
- **Could:** 항목 검색은 소식 검색과 분리하며 기간·영역·상태·담당자 등의 조건을 제공하고 삭제된 항목은 일반 검색에서 제외한다.

## 8. 현황판 · 근거 · 변경 이력 정책

**관련 기능:** `DASH-01` · `DASH-02` · `DASH-03` · `DASH-04` · `DASH-05` · `DASH-06` · `HIST-01` · `HIST-02` · `HIST-03` · `HIST-04` · `HIST-05`

### 8.1 현황판 구성

| 영역 | 표시 기준 |
| --- | --- |
| **예정·지난 일정** | 유효한 예정 일정과 날짜가 지난 미완료 일정 구분 · 완료·취소·삭제된 일정을 예정 일정처럼 표시하지 않음 |
| **남은 할 일** | 미시작·진행 중 할 일과 담당자 표시 · 완료·삭제 항목 제외 |
| **미확인 확인사항** | 소유자 확인 전 질문 표시 · 답변이 제출되었어도 승인 전에는 유지 |
| **최근 변경** | 소유자가 반영한 변경과 담당자의 허용된 상태 변경 표시 · 승인 대기 요청과 구분 |

- 반영·담당자 변경·상태 변경·삭제 이후 조회하는 요약 영역은 같은 최신 결과를 보여야 한다.
- 상충 항목은 현재 값을 유지하되 **확인 필요**를 표시한다.
- 원본 삭제로 재확인 대상으로 표시된 항목은 소유자가 다시 확인할 때까지 현황판에서 제외한다.
- **Should:** 새 참여자는 브리핑에서 현재 정보를 빠르게 파악하고 관련 항목으로 이동한다.

### 8.2 근거와 변경 전후

- 항목 상세에서 원본 근거 또는 가족이 직접 입력한 근거를 확인한다.
- 생성·수정·담당자·상태 변경·해소·일반 삭제에 대해 변경자·시점·근거를 남긴다.
- 제안 화면에서는 **적용 전 비교**, 이력 화면에서는 **이미 확정된 변경의 전후 비교**를 제공한다.
- 원본 삭제로 제거한 내용은 과거 값·비교 화면·인용문에서도 다시 보여주지 않는다. 삭제 사실과 남아 있는 유효 근거만 안내한다.
- **Could:** 서비스 전반의 열람·편집 활동 기록은 핵심 변경 이력과 별도 기능이며 범위·열람 권한·보관 기간을 상세 설계한다.
- **Could:** 변화 흐름 시각화에도 같은 권한·삭제 기준을 적용한다.

## 9. 카카오톡 공유 · 외부 진입 정책

**관련 기능:** `SHARE-01` · `SHARE-02` · `SHARE-03` · `SHARE-04` · `SHARE-05` · `SHARE-06` · `SHARE-07` · `SHARE-08` · `SHARE-09`

### 9.1 공유할 내용과 카드

- 가족이 유효한 확정 항목·변경을 직접 선택하고 공유 카드 미리보기를 확인한다.
- 검토 중 제안·승인 요청을 확정 사실처럼 공유하지 않는다. 삭제·근거 재확인 중인 항목은 새 공유 대상에서 제외한다.

| 카드에 포함 | 카드에서 제외 |
| --- | --- |
| **항목 유형 · 변경 여부 · 서비스 링크** | 부모님 이름 · 증상 · 원문 · 상세 돌봄 정보 |
| 예: **일정 · 변경 있음 · 한마음에서 확인** | 구체적인 예약일·병원·담당자 등 상세 값 |

- 민감한 상세 내용은 서비스 내부에서 로그인·공간 참여를 확인한 뒤 보여준다.
- 사용자가 카카오톡에서 수신자·채팅방을 직접 선택한다. 전송 취소·실패 시 재시도를 안내한다.
- 카카오톡 대화 자동 수집과 메시지 자동 발송은 제공하지 않는다.

### 9.2 공유 링크 접근

| 진입한 사용자 | 처리 |
| --- | --- |
| 로그인한 현재 구성원 | 최신 확정 정보 조회 |
| 미로그인 사용자 | 돌봄 상세를 숨기고 로그인 안내 |
| 로그인했지만 비구성원 | 상세 열람 차단 · Should 기능으로 유효한 초대를 통한 참여 안내 |
| 공간에서 나가거나 제외된 사용자 | 기존에 받은 링크여도 접근 차단 |
| 항목 삭제 / 공간 삭제 | 삭제·접근 불가 안내 · 상세 내용 노출 금지 |

- 공유 링크는 초대장이 아니다. 보유만으로 공간 가입·열람 권한을 얻지 못한다.
- **Should:** 로그인과 유효한 초대를 통한 참여를 마치면 원래 공유 대상으로 연결하고 권한을 다시 확인한다.
- 이미 보낸 카드의 링크도 **접근 시점의 최신 정보**를 보여준다. 삭제된 원문·파생 내용은 다시 노출하지 않는다.
- 외부 채팅방에 이미 전달된 카드는 서비스에서 회수할 수 있다고 가정하지 않는다. 카드에는 처음부터 최소 정보만 넣는다.

### 9.3 공유된 확인사항 답변 · Should

- 로그인과 현재 공간 참여를 확인한 뒤 해당 질문·상태·답변 화면으로 연결한다.
- 구성원이 제출한 답은 기존 확인사항의 승인 요청으로 남기고, 소유자 확인 후 해소한다.
- 빠른 진입을 제공하더라도 익명 열람·익명 답변·자동 해소는 허용하지 않는다.

## 10. 알림 · 공통 접근 정책

**관련 기능:** `NOTI-01` · `NOTI-02` · `NOTI-03` · `NOTI-04` · `NOTI-05` · `COMMON-01`

### 10.1 서비스 내부 알림 · Should

- 첫 알림 채널은 **서비스 내부 알림**이다. 이메일·모바일 푸시는 이번 알림 구현 범위에 포함하지 않는다.
- 본인에게 배정된 할 일 관련 알림을 기본 수신 대상으로 두고, 개인별 수신 여부·변경 유형·범위를 조정한다.
- 모든 변경을 모든 가족에게 기본 발송하지 않는다.
- 승인 대기 요청은 확정 변경 알림으로 보내지 않는다.
- 같은 변경·수신자에 대한 알림은 한 번만 생성한다.

### 10.2 읽음과 상세 진입 · Should

- 본인의 알림 목록과 읽음 여부를 관리한다. 알림 읽음은 할 일 완료·확인사항 해소와 별개다.
- 알림에서 상세로 이동할 때 현재 참여 권한과 항목 상태를 다시 검증한다.
- 원본 삭제 시 알림에 복사된 민감 내용도 제거하고, 삭제된 정보로 다시 접근하지 못하게 한다.

### 10.3 홈 화면 설치 · Could

- 지원되는 모바일 환경에서 홈 화면에 추가해 서비스에 빠르게 진입하도록 제공한다.
- 현황판에 종속되지 않는 **Common 공통 접근 기능**으로 분류한다.
- 홈 화면 설치가 오프라인 돌봄 정보 조회·수정을 의미하지 않는다. 오프라인 이용은 이번 범위에서 제외한다.

## 11. 삭제 · 탈퇴 · 연결 정보 처리 정책

**관련 기능:** `AUTH-05` · `SPACE-09` · `SPACE-10` · `SPACE-14` · `REC-10` · `REC-11` · `ITEM-15` · `HIST-01` · `HIST-02` · `HIST-03`

### 11.1 삭제 유형별 기준

| 작업 | 실행 주체 | 데이터 처리 |
| --- | --- | --- |
| **관리 항목 삭제** | 소유자 · 구성원은 요청 | 일반 목록·현황판에서 숨김 · 삭제 표시와 변경 이력 유지 |
| **소식 원본 삭제** | 현재 참여 중인 작성자 또는 소유자 | 원문과 해당 내용을 복사한 제안·항목·이력 등을 함께 제거 |
| **공간 나가기 / 내보내기** | 본인 / 소유자 | 참여 권한 종료 · 공유 기록과 완료 이력 유지 · 미완료 담당 업무 해제 |
| **공간 전체 삭제** | 소유자 | 공간에 속한 소식·항목·제안·이력 등 전체 삭제 · MVP 복구 미제공 |
| **회원 탈퇴** | 본인 | 계정 기본 정보·소셜 연결·인증 정보 삭제 · 공유 돌봄 기록은 별도 기준 적용 |

### 11.2 소식 원본 삭제

1. 삭제 권한과 현재 공간 참여 상태를 확인한다.
2. 연결된 항목·제안·이력 등 영향 범위를 안내한다.
3. 원문과 해당 원문을 인용·복사한 내용을 제거한다.
4. 영향받은 항목의 남아 있는 근거를 확인하고 재확인 상태·현황판 노출을 조정한다.
5. 원문을 담지 않은 삭제 행위자·시점 등 최소 기록만 남긴다.

> **원본 삭제는 링크만 끊는 처리가 아니다.**
>
> - 제안·근거·변경 전후 이력·요약·알림·관리 항목에 복사된 해당 내용도 함께 제거한다.
> - 원본 작성자의 삭제 권한으로 발생한 연결 정보 정리는 소유자 승인 대기로 미루지 않는다.
> - 일반 항목 삭제 시 이력을 보존한다는 규칙보다 **원본 삭제에 따른 내용 제거 규칙을 우선**한다.

### 11.3 남아 있는 항목과 재확인

- 현재 항목 내용이 삭제된 원문에 의존하면 다른 유효한 독립 근거가 남아 있어도 해당 내용을 가리고 재확인 대상으로 표시한다. 삭제의 영향을 받아 유효한 근거가 하나도 남지 않은 항목도 재확인 대상으로 표시한다.
- 재확인 대상은 소유자가 다시 확인하기 전까지 현황판과 새 공유 대상에서 제외한다.
- 현재 내용이 삭제된 원문에 의존하지 않고 유효한 독립 근거가 남아 있으면 현재 내용을 유지한다. 삭제된 원문의 사본을 유효 근거로 취급하지 않는다.
- 소유자의 재확인은 삭제된 내용을 되살리는 동작이 아니다. 남아 있는 유효 근거 또는 새로 확인한 입력을 기준으로 판단한다.
- 검색·요약·비교 화면·AI 재시도·늦게 도착한 분석 결과를 통해 삭제된 내용이 다시 나타나지 않도록 처리한다.

### 11.4 공간 삭제

- 소유자가 공간 전체 삭제 범위를 확인한 뒤 실행한다.
- 해당 공간의 원본·관리 항목·제안·근거·변경 이력과 연결된 사용자 노출 자료를 함께 삭제한다.
- 이후 구성원과 기존 초대·공유 링크를 통한 접근을 차단한다.
- MVP에서는 공간 복구 기능을 제공하지 않는다.

### 11.5 회원 탈퇴

- 소유 중인 모든 공간에 대해 **소유권 이전 또는 공간 삭제**를 먼저 완료한다.
- 계정 기본 정보·소셜 연결·인증 정보를 삭제하고 로그인·참여 권한을 종료한다.
- 남겨진 공유 돌봄 기록과 이력의 작성자는 **탈퇴한 사용자**로 표시한다.
- 회원 탈퇴만으로 가족 공간 전체 또는 모든 공동 기록을 자동 삭제하지 않는다. 원본 삭제·공간 삭제는 각 작업의 별도 절차를 따른다.
- 탈퇴 안내에서 계정 정보 삭제와 공동 기록 처리의 차이를 보여준다.

## 12. 상태 값 총정리

> 사용자에게 보이는 상태와 전환 기준은 이 문서를 따른다. 아래 영문 식별자는 **설계 참고 이름**이며 실제 DB·API 명칭은 상세 설계에서 통일한다.

| 구분 | 상태 / 표시 | 판단 기준 |
| --- | --- | --- |
| 공간 역할 | OWNER · MEMBER | 공간마다 소유자 한 명 |
| 관리 항목 유형 | 일정 · 할 일 · 확인사항 · 관찰 · 안내 | AI 후보와 확정 항목 구분 |
| 할 일 | 미시작 · 진행 중 · 완료 | 소유자 또는 현재 담당자가 허용된 전환 수행 |
| 일정 | 예정 · 완료 · 취소 | 소유자 확인으로 상태 확정 |
| 일정 시간 표시 | 예정 시점 전 / 지난 일정 | 날짜·시간에서 계산 · 완료 상태와 별개 |
| 확인사항 | 미확인 · 확인됨 | 답변 제출과 소유자의 해소 확정 구분 |
| AI 제안 | 검토 대기 · 반영 · 미적용 · 무효 | 선택 해제는 유효한 제안의 검토 대기를 유지 · 원본·대상·근거 또는 검토에 사용한 항목 버전이 유효하지 않으면 무효 |
| 변경 요청 | 승인 대기 · 반영 · 미적용 · 취소 · 무효 | 소유자가 반영·미적용 결정 · 제출자가 승인 대기 요청 취소 · 제출 당시 참여가 종료되거나 원본·대상·버전 검증에 실패하면 무효 |
| AI 분석 | 진행 · 완료 · 실패 | 분석 완료와 관리 항목 반영은 별개 |
| 상충·근거 표시 | 확인 필요 / 재확인 필요 | 항목의 완료·취소 상태와 별도 표시 |
| 편집 잠금 | 없음 / 해당 사용자 편집 중 | 항목 단위 · 해제 요청 없이 갱신이 중단되면 유효시간 만료 시 해제 · 다시 편집할 때 잠금·권한·버전 확인 |
| 삭제 표시 | 일반 삭제됨 / 원본 삭제로 내용 제거 | 보존·제거 범위는 11장에 따라 구분 |
| 알림 | 안 읽음 · 읽음 | 읽음으로 업무 완료·확인사항 해소 금지 |

> **서로 다른 상태를 하나로 합치지 않는다.**
>
> - 일정 날짜가 지남 ≠ 일정 완료
> - 답변 제출 ≠ 확인사항 해소
> - AI 분석 완료 ≠ 제안 반영
> - 편집권 보유 ≠ 소유자 승인 권한
> - 알림 읽음 ≠ 할 일 완료

## 13. MVP 범위 · 제외

**관련 기능:** `AI-12` · `AI-13` · `AI-14` · `AI-15` · `AI-16` · `PROP-09` · `REC-09` · `ITEM-13` · `SHARE-08`

- 기능 명세서 기준 **11개 분류 · 100개 항목**. 이 중 Won’t는 구현 제외 항목이며 100개 모두를 MVP에서 개발한다는 뜻은 아니다.

| 우선순위 | 항목 수 | 적용 범위 |
| --- | --- | --- |
| **Must** | 67 | 인증·공간·권한, 소식과 핵심 AI 분석, 소유자 승인, 항목·현황판·근거·이력, 기본 공유, 삭제·탈퇴 |
| **Should** | 15 | 음성, 부모님 동의 요청, 질문 응답·브리핑·추가 질문, 공유 답변·참여 안내, 내부 알림 |
| **Could** | 9 | 문서 인식, 소식·항목 영역 분류와 상세 검색, 세부 권한, 활동 기록·시각화, 홈 화면 설치 |
| **Won’t** | 9 | 아래 제외 목록 |

### 13.1 이번 MVP에서 구현하지 않는 기능

| 기능 ID | 제외 기능 |
| --- | --- |
| AI-12 | 건강 상태 판단·진단 |
| AI-13 | 약 용량 변경·치료 방법 안내 |
| AI-14 | 장기요양등급 예측 |
| AI-15 | 공식 제도·혜택 안내 |
| AI-16 | 진료용·심사용 문서 생성 |
| PROP-09 | AI 자율 정보 확정 |
| REC-09 | 카카오톡 대화 자동 수집 |
| SHARE-08 | 카카오톡 자동 발송 |
| ITEM-13 | 위치 추적·기기 연동 모니터링 |

- 한마음은 가족이 남긴 정보의 정리·갱신·협업을 지원한다. AI가 의료적 판단이나 제도 판정을 대신하지 않는다.
- 제외 기능은 이후 제공을 약속하는 목록이 아니다.

### 13.2 범위 변경 기준

- Should·Could 기능을 구현할 때에도 동일한 권한·승인·근거·삭제 정책을 적용한다.
- 기능 우선순위나 제품 정책을 바꿀 때 관련 기능 ID와 영향을 받는 화면·데이터·상태 전환을 함께 검토한다.
- 기획서의 결제·가족 구독·기관 확장 구상은 이번 핵심 MVP 기능과 분리해 검증한다.

## 14. 후속 설계 항목 · 문서 관리

### 14.1 상세 설계에서 정할 운영값

> 아래는 핵심 권한·승인 원칙을 다시 결정하는 항목이 아니라, 구현·운영 준비 과정에서 수치와 절차를 구체화할 항목이다.

| 항목 | 정할 내용 |
| --- | --- |
| 편집 잠금 | 서버 기본 유지 시간 2분 · 권장 갱신 간격 30초 · 접속 종료로 갱신이 중단되면 유효시간 만료 시 해제 |
| 사용량·한도 | 현재 공간 생성 개수·초대 사용 횟수·공간 인원 제한은 두지 않는다. 호칭은 1\~30자로 확정. 그 외 입력 길이·AI 재시도·사용량 한도 등은 별도 합의 |
| 요금·플랜 | 기획서의 무료 공간·가족 구독 구상을 실제 사용·비용 데이터로 검증한 뒤 한도·가격 결정 |
| 삭제 운영 | 백업·로그·검색 인덱스·AI 제공자 측 보관 데이터가 있다면 삭제 범위·처리 시점·복원 시 삭제 재적용 방식 정의 |
| 추가 활동 기록 · Could | 열람 기록 수집 범위·열람 권한·보관 기간 |
| 상세 입력 검증 | 항목 유형별 필수 값·길이·날짜 입력 범위와 오류 안내 |

- 실제 돌봄 데이터를 받기 전에는 동의 절차와 삭제 처리 범위를 준비한다.
- 사용자 화면·API는 문서에 없는 숫자 제한이나 상태 전환을 각자 정해서 적용하지 않는다.

### 14.2 기능 명세서와 함께 관리

- 각 장의 **관련 기능 ID**를 기준으로 기능 명세서와 정책을 함께 검토한다.
- 정책 변경 시 관련 기능 설명·상태 표·권한 표를 같이 수정하고 개정 내용을 남긴다.
